# S8192 full-system calibration

This is a code and measurement record only. The payloads, manifests, JSONL
runs, and checkpoints used here remain under `/tmp` and are not repository
artifacts.

## Runtime and command

The run used eight B300 GPUs with the repository's canonical configuration,
raw-byte loader, FP8 Transformer Engine path, FBT two-pass objective, sparse
LatentMoE, MSAR, CUDA graphs, DDP reduction, and AnchorMuon/AdamATan2 update.
The usable runtime was `/tmp/hnet-venv` with PyTorch `2.10.0+cu130`, CUDA 13.0,
cuDNN `9.23.2`, Transformer Engine checkout
`9646c3ef22455b6948cbe870f1aaf20fc8238d69`, and cuBLASLt version code `130802`.

The calibration command was:

```sh
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
/tmp/hnet-venv/bin/torchrun --standalone --nproc_per_node=8 \
  train_hnet_600m.py --manifest /tmp/hnet_s8192_fixture_128/train.manifest.json \
  --seq 8192 --auto-batch-max 16 --steps 1 --warmup 1 \
  --eval-every 0 --log-every 1 --ckpt-every 0 \
  --out /tmp/hnet_s8192_calibration_max16.json \
  --checkpoint /tmp/hnet_s8192_calibration_max16.pt
```

The temporary fixture contains 128 document-local records of 10,000 bytes
each, so every tested per-rank batch has enough complete rows on every rank.

## Results

The batch sweep executes four complete eager FP8/DDP/optimizer updates for each
candidate and restores model, optimizer, RNG, and FP8 scaling state between
candidates. Peak power is the maximum rank reading over the final two updates.

| per-GPU batch | peak power (W) | graph result |
| ---: | ---: | --- |
| 1 | 279.0 | complete |
| 2 | 283.2 | complete |
| 4 | 295.0 | complete |
| 8 | 317.4 | complete |
| 16 | 356.3 | complete |
| 32 | 418.6 | eager calibration complete; graph capture OOM |

The graph-validated selection is therefore `B=16`, even though it remains below
the 1 kW target. The separate complete graph step at `B=16, S=8192` was finite:
`1620.2 ms`, `0.65M` aggregate tokens/s (about `81k` tokens/s/GPU), and no
nonfinite metrics. The earlier `B=8` graph step was also finite at `1305.5 ms`
and `0.40M` aggregate tokens/s.

After moving the FP32 router probabilities into TE's fused mask-map unpermute,
a fresh three-step full run remained finite at the same shape. It measured
`1576.9`, `885.1`, and `706.1 ms` for steps 1–3 respectively; the final step
reported `1.485M` aggregate tokens/s (`185.6k` tokens/s/GPU). The first step
includes graph optimizer initialization, so the final two steps are the useful
steady-state comparison. The change removed one padded expert-row weighting
kernel per MoE call and was independently checked for eager output/gradient
parity and CUDA-graph replay parity.

At `B=32`, eager calibration remained finite, but graph capture failed on the
MSAR path while allocating a 96 MiB tensor: each B300 had only about 78 MiB
free with 262.97 GiB allocated. The trainer correctly failed closed rather than
silently switching to eager execution. This establishes the current memory
limit for the complete S8192 graph shape; it is not evidence that B32 is a
usable production batch.

The graph capture warmup also emitted PyTorch's
`AccumulateGrad` stream-mismatch warning. It did not produce a nonfinite result,
but it remains a CUDA-graph/DDP audit item before relying on longer runs.

The matching eight-rank document-local loader benchmark at `B=16, S=8192`
used direct DMA into persistent buffers and measured `0.435 ms` at the slowest
rank over eight steps (`603 MB/s` of byte payload). This isolates input staging;
it is not a model training throughput number.

## Policy

`CANONICAL_MAX_BATCH=16` is now the production calibration bound. Raising it
requires a capture-aware candidate test or a measured reduction in graph memory;
power-only eager calibration is insufficient. No throughput number from the
older S4096 runs is extrapolated to S8192.
